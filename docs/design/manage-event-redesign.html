The host panel is the last screen still built in the old language — a 160pt thumbnail inside a white card, under two ringed promos. This gives the event its photo full-bleed at screen-width square and drops the whole page onto it as one smoked-glass sheet. Not a new invention: it is the profile sheet, which already ships, pointed at the thing DESIGN.md §7 says the event hero should have been all along.

01 The photo is the screen

Full-bleed, screen-width square, running under a title-less header. That ratio is not a guess — DESIGN.md §7's unbuilt event-sheet item specifies "a screen-width square at full-screen" for exactly this hero. Profile uses 4:5 because a person is a portrait; an event is a place.

Title, time and place move onto the image at TYPE.display, with the eyebrow's coral dot doing the live/ended state. The header loses its title entirely and becomes two 46×46 onPhoto chips — the one chip size the app uses everywhere. The white info card, the 160pt cover, the CategoryTile and the going-pill all disappear; the category survives as a small pill top-right, where it stops repeating itself.

02 The sheet, and everything that lives on it

One <Glass tier="onPhoto" radius={32} edge="top">, pulled up so its corners sit over the photo's last 32pt. Every card inside it is a translucent white lift — fillOnDark over borderOnDark — never another <Glass>. A blur inside a blur is a native blur view per row and reads as mud; DESIGN.md §3 is explicit about this and profile already does it right.

The pulse strip replaces four scattered copies of the same numbers: the going-pill on the card, the Wishlisted · 12 header, and the stats row inside BoostCard's boosted state. The requests figure goes coral above zero and stays white at zero — that is the entire attention mechanism, and nothing else on the live screen is coral except the Approve buttons it points at.

The action tiles replace two ringed promos and the black button at the bottom. The surface is identical on all three; only the glyph is coloured. A saturated ring around a whole card shouts — a 17pt glyph in a tinted well does not.

No sub-labels. QR, 2 left and 6 in are gone; state is a dot on the glyph well instead. A tile is a door, and a door does not need a caption — the dot says "there is something here", which is all a host needs to decide whether to open it. Boosted is the one state a dot cannot carry, so it is carried by the well going solid BOOST_ACCENT with a white flame (middle tile above). Colour for a persistent state, a dot for a transient one.

Two things the dot needs before it can ship

The dot is coral, not red. COLORS.error (#EF4444) sits 8° from COLORS.primary (#F95B5B) and putting them on the same row reads as two rival reds. This marks "something here", not "something wrong", so it takes primary. Say if you want error anyway.

Chat has no unread source. queryKeys carries unreadDms and unreadDmCounts — both DM-only. There is no per-event-thread unread count, so the chat tile can never dot until one exists. Either add it, or accept that only two of the three tiles ever badge. I have drawn it badged; that is a promise the data cannot currently keep.

Sheettier="onPhoto" · radius={32} · edge="top" · SHEET_UNDERHANG 500
FrostThe same photo again, blurRadius={60}, + COLORS.inkVeil (0.28, not scrim — the photo's colour has to carry through)
LiftsfillOnDark 0.08 / borderOnDark 0.14, radius 20. Glyph wells use fillOnDarkStrong or the accent at ~0.20.
Textwhite → textOnDark → textOnDarkMuted. The ink ramp never appears on this surface.
CoralApprove buttons and the requests count. Nothing else, on the live page.
The one call worth arguing about

"Open event chat" loses its full-width button. It is a door, not a decision, and it was competing with the per-row coral Approves for the page's one moment of emphasis. The live screen ends up with no full-width CTA — correct, because a host makes no single decision here. If chat turns out to be the most-tapped thing on the screen, promote it and demote check-in; do not add a second CTA.

04 Wishlist: the same stack, frosted until you pay

The gold-ringed banner is gone. Locked, the section is the same row stack as requests and attendees, frosted over, with the crown and a Mello+ pill centred on the frost. Unlocked, the frost lifts and you get real rows — avatar, name, tappable to the profile. Not the chip cloud it is today: one row treatment for all three people-sections on the page.

Which also answers what the count is for. It stays in the header and the pulse strip; the frost is what makes twelve feel like twelve people rather than a number.

The rows behind the frost are placeholders, and they have to be

getEventSavers is enabled: isHost && premium — a free host never receives the saver list. So there is nothing real to blur, and that is the correct design, not a limitation to work around. A blur is a visual effect, not a security boundary: fetch the names to blur them and they are sitting in the response, in the query cache and in the component tree, one React DevTools session from being read. Do not enable that query for non-premium hosts. Placeholder rows driven by saversCount — real count, no real identities.

Use SkeletonPersonRow — it landed while this spec was being written

5aa65af added SkeletonGroup / SkeletonBone to ui/ and a set of composed shapes in components/skeletons/. SkeletonPersonRow is described in its own header as "the shape behind friends, blocked, attendees, search results" — which is this, exactly. Wrap it in a group so every bone shares one clock rather than starting its own driver and drifting out of phase.

Its avatar bone is 44 where the sheet's rows are 38. Leave it. The stack sits behind a blur pane; 6pt on a shape nobody can resolve is not worth a prop.

But the bones are the wrong colour on this surface — the same bug as finding 1

COLORS.skeletonBone is rgba(15, 24, 44, 0.10) on the light palette: dark ink, for a light surface. The locked wishlist sits on the onPhoto sheet, which is dark in both themes — so on the light theme these bones would be near-invisible. It is exactly the trap ParticipantRow's #F0F1F3 fell into, one level up.

Add the on-dark pair to both palettes with the same value in each — the way fillOnDark and borderOnDark already are, because they describe a surface that does not change: skeletonBoneOnDark: 'rgba(255,255,255,0.09)', skeletonSheenOnDark: 'rgba(255,255,255,0.16)'. The dark palette's existing values already are these; copy them up. Then give SkeletonBone an onDark prop and thread it through SkeletonPersonRow. Add the prop, do not fork either component — and ship it as its own commit, because ui/ has other callers.

Photo-less: the category tint becomes the hero

04 When there is no photo

eventImageUri(event) returns null often enough that this is not an edge case, and a design where the photo is the screen has to answer for it. The hero keeps its shape and its type; the image becomes the category tint as a full-bleed field with a large, low-opacity ActivityGlyph washed across it.

The sheet then frosts itself from that field instead of from a photo — which works identically, because blurring a gradient gives you a gradient. The existing code already reaches for this fallback at a smaller size and for the same reason: the comment at host:161 says it exists so a photo-less event does not look like it failed to save one.

Two things I did not build, both because they change a promise

"Event feedback should be public." The 👍/👎 counts already are — that panel is what shows them. Attributing votes already cast under that promise is the part I would not ship without a deliberate decision — it needs a schema change plus a cutover where old submissions stay anonymous. Say the word and I will spec it separately.

Expired requests. A pending request on an ended event currently still renders a live Approve. Approving someone into an event that already happened is not a thing a host means to do, so it collapses to one muted line — "3 requests expired". UI-only, no service change, but it is a behaviour change and worth your yes.

Profile is the only screen in the app where a photo owns the viewport, and the comments in it record two failed versions and the reason each one failed. The three animated styles

StyleWhat it doesWhy it is separate
photoStyle y < 0 → scale(1 - y / photoHeight)
y ≥ 0 → translateY(y * 0.5)		 Two branches, one job: the photo's bottom edge never parts from the sheet. Pull-down grows it upward by exactly the overscroll so it still reaches the top; scroll-up lags it at half speed so the sheet visibly catches it.
kenStyle scale(1 → 1.07) over 24s, repeating, reversed Its own layer inside the parallax one. The two motions have different origins — parallax scales from the bottom to stay welded, the drift scales from the centre so it creeps. Combining them into one transform breaks both.
frostStyle translateY(scrollY - photoHeight + SHEET_RADIUS) The frost lives inside the sheet, and the sheet scrolls — so it is counter-translated by exactly the sheet's own offset, pinning it to the screen. Real glass does not drag its reflection along with it.

Where an event differs

01 · RatioHERO_RATIO = 1. The only constant that changes.
02 · CaptionThe one structural addition. Profile's name lives in the sheet; an event's title belongs to the image. It is a sibling of photoInner, anchored to the window's bottom — not a child. As a child it would inherit the pull-down scale and the title would balloon on overscroll. Anchored to the window, it stays welded to the sheet's lip and the photo parallaxes behind it.
03 · FallbackProfile falls back to <Avatar size={96}>; an event falls back to the category tint + ActivityGlyph. Drop Ken Burns and the parallax there — motion on a flat field is motion you can see is fake — and render the hero at 16:9, because a square of flat colour is a lot of nothing.
04 · Backdrop when there is no photoDo not copy profile's : undefined here. Profile can drop the backdrop because its fallback fills the whole hero; on an event the shorter 16:9 field would leave the sheet doing a real backdrop-blur of the screen behind it, and printing an edge where the field stops. Pass a plain <View> of the category tint instead — a blurred flat colour is the same flat colour, for free.
05 · Bottom insetProfile adds tabBarInset. This route is outside the tab navigator, so it is insets.bottom — and <Screen edges={['top']}> must not also inset the bottom, or it is padded twice.
06 · Tap targetProfile's window is a Pressable opening the photo viewer. Leave the event hero inert for now: a lightbox is a new surface and this spec is a reskin. Keep the window a plain <View> so nobody has to unpick a gesture later.
Porting this also deletes the blocker from the first draft

<AppBackground> is mounted in app/(tabs)/_layout.tsx:504 and once more in app/profile/settings.tsx. This route is outside the tabs tree, so its floor is a flat #F2F2F4 — an ordinary <Glass> panel here would blur flat grey and render as a white box.

A backdrop pane composites its own blurred copy instead, so what sits behind it stops mattering. No third <AppBackground>, no blob-phase artifact, no transparent-Screen change. It fixes Android too: backdrop needs no platform blur, because an image blur is ordinary image processing — DESIGN.md §7 names it as the one glass surface that should render the same on both. The prettier direction is also the lower-risk one.

Two rules that fail silently if you get them wrong

The photo must stay inside the scroller. Moving it out and pinning it looks identical at rest and wrong the moment you scroll — the sheet slides across an image that never moved, which is the version profile's comments record as reading like "two unrelated planes".

transformOrigin: 'bottom' on photoInner is load-bearing. Without it the pull-down scale grows the photo from its centre, its bottom edge lifts off the sheet, and a sliver of whatever is behind shows through the join. No error, no crash — just a hairline that appears only while you are dragging.
